**Slice 2 — portfolio absence counters** (`backend/app/portfolio_absence.py`,
`GET /api/portfolio/absence`, `frontend/src/portfolioAbsence.js`, `views/AbsenceStrip.jsx`; 13
backend, 7 frontend tests).

- **D-259 — Absence is four independent counts that never combine, and the payload says so.**
  `basis` ships on the response — "They are independent and do not combine into a coverage score" —
  rather than being left to the view, because the strip is the one place four numbers sit in a row,
  which is exactly where a reader starts adding them up. There is no total, no percentage, and no
  ratio anywhere in the module.
- **D-260 — Every counter ships the records it counted, not just the number.** `_counter` returns
  `records` beside `count` (§4.2 rule 4). A count an operator cannot open is an accusation they have
  no way to answer — and a count over our own record-keeping is not a claim about the customer, so
  the only honest response to it is "show me which ones".
- **D-261 — The sentence is authored on the server, count and window together.** `_counter` builds
  "62 accounts with no recorded interaction in 30 days" as one string. The count and the window are
  both server facts and a view that assembles "62 accounts" and "in 30 days" separately is a view
  that can render one without the other. The window is validated to 1–365 days and echoed back with
  its `since` date and the default it departed from.

**Slice 5 — presentation** (`frontend/src/inlineCitations.js`, `viewScope.js`,
`backend/app/short_ref.py`, evaluator config on readiness components; 18 backend, 18 frontend tests).

- **D-262 — Inline citation chips render the packet ids the claims block already links, and nothing
  else.** `copilot_model` already writes `[p003]` into the answer body; this turns that existing
  token into a chip and **introduces no new mapping**. A bracket the claims block does not cite
  stays literal text — that case is an upstream validation failure, and dressing it up as a working
  citation would hide the failure behind the affordance meant to expose it. The chip spends no
  colour. Not applied to `shared_plan`'s artifact despite §7.1 naming it: that generator carries no
  claim→source links, so building the chip there would mean inventing the mapping this module exists
  to avoid.
- **D-263 — The evaluator's configuration is reported beside the reading as configuration, never as
  a second reading.** A component names its evaluator but not what it was asked to look for, which
  is worst in the case readiness designed for — an unknown evaluator key fails closed into
  `coverage: partial`, so nothing ran and the config is the only thing left that could explain the
  degraded reading. Tests assert the config survives the evaluator's absence and that it stays the
  definition's own values: a config is an **input**, so nothing on it may claim a state.
- **D-264 — The config is attached outside both branches, so the failure path cannot lose it.**
  Attaching it where the evaluator succeeds would drop it in precisely the case it explains.
- **D-265 — Short reference ids are derived on the server over the whole population, never per
  list.** `short_ref` widens the token until no two ids in the set collide; identical ids keep their
  full id. Two properties are load-bearing and both require the server: a reference unique only
  within the list on screen is worse than none, because two people would each be certain they meant
  the same object; and the same definition must get the same token in the plan, the readiness
  detail, and the definitions listing. It is a name — never a sort key, never an ordering.
- **D-266 — The saved-view scope strip is hueless, and the client may author its sentence.**
  `.coverage-callout`'s `is-warning` / `is-healthy` is right for a coverage claim and wrong here: a
  filter the operator chose is not a fault. And D-153's rule — a view that composes part of a
  refusal can soften one — does not reach this sentence, because it withholds nothing: every row is
  in hand and clearing the filter shows them all. If the narrowing ever moves server-side, the
  sentence moves with it. It states the count and never scores it.

**Slice 3 — playbook entry instantiation counts in the upgrade preview** (`playbooks._entry_usage`;
8 backend tests).

- **D-267 — The preview reports two planning counts per entry and runs no evaluator.** Both come
  from `readiness_plan_instances`: an instantiation is a row a plan created, and `recorded_complete`
  is an operator-recorded tick carried from a legacy checkbox. Neither is a readiness state, and
  calling `readiness.evaluate` here would be both expensive and a category error — the preview asks
  a question about the plan. A test monkeypatches `readiness.evaluate` to raise and asserts the
  preview still returns. Nothing divides one count by the other; there is no completion rate.
- **D-268 — Zero is a row, and the scope is named once beside the counts.** A step that has never
  fired is exactly what an operator deciding whether to keep it needs to see, so an entry with no
  instantiations ships `0` rather than being omitted. `_ENTRY_USAGE_SCOPE` — "live plans across
  every account" — is a single constant the label and the query both read, because a count over this
  account and a count over every account are different numbers and the preview must not be able to
  describe one while computing the other.

**Slice 4 — plan variance, stated honestly** (`frontend/src/requirementDetail.js::planVariance`;
5 backend, 8 frontend tests).

- **D-269 — A variance is only computed when both operands are planning facts.** `due_date` and
  `recorded_complete_on` are both planning facts, so their difference is one too — that is the only
  branch that subtracts anything. Every other row returns the planned date and its age as one
  statement, with the readiness state beside it in readiness's own vocabulary. `assessed_through` is
  the date evidence was assessed **through**, not the date a requirement became true, and it is
  never read here under any label — a frontend test asserts its value does not appear anywhere in
  the result, and a backend test asserts the server ships no variance of its own and no key outside
  the completion allowlist implies completion. This is §2.2's correction: the original proposal was
  half honest, and this is the honest half.
- **D-270 — The delta is hueless and rendered outside the tone wrapper.** `planStatus` reports
  `risk` on an overdue row and a delta that inherited that hue would be asserting that late is a
  status; a step recorded a week early and one recorded a week late are the same kind of planning
  fact. A scheduled row whose anchor never resolved gets the cross-hatched unknown treatment, and
  the relative rule is deliberately **not** offered in its place — "2 days after the kickoff date"
  reads as an answer to "when", and with no kickoff date it is not one. A test asserts that sentence
  contains no digits.

**Slice 6 — advocacy tags on people** (`0054_advocacy_tags.sql`, `people_core.advocacy_tags`,
`POST /api/advocacy-tags`, `views/PersonCard.jsx`; 9 backend, 6 frontend tests).

- **D-271 — A new table, not more kinds on `advocacy_events`.** Two reasons, both recorded in the
  migration header. (1) `advocacy_events` is *internal* advocacy and is read by name with its own
  `kind IN (...)` filter in four places — `people_core.has_champion_evidence`, `people_analytics`,
  `stage75`, `readiness._CHAMPION_EVIDENCE_KINDS`. Widening the CHECK needs all four updated in
  lockstep, and the one that got missed would start counting a conference talk as proof that someone
  advocates for us when we are not in the room — which is the entire point of the coach-vs-champion
  gate. (2) §8 requires the date and the evidence note *structurally*, and `advocacy_events`'
  equivalents are nullable with existing rows; tightening them means a rebuild that either fails or
  backfills a date nobody recorded. A test asserts the new kinds never appear in `advocacy_events`'
  DDL, and `has_champion_evidence` is asserted `False` for a person carrying only a public tag.
- **D-272 — The date and the note are required by CHECK, not only by NOT NULL.** `NOT NULL` alone is
  satisfied by `''`, which is how a required field becomes an optional one without anyone editing
  the schema. The Pydantic model repeats both with `min_length=1` so the 422 names the field instead
  of the request reaching SQLite and returning an integrity error; tests assert missing, `""`, and
  `"   "` are all refused at both layers.
- **D-273 — The kind list is closed and there is no score, level, or sentiment column.** An `other`
  member would be the free-text escape hatch §9 refuses, since "other: very keen" is a sentiment
  about a named person in a field nobody validates. The test asserts the column set **exactly**, so
  a later addition has to argue with a test rather than slip in, and separately bans any column
  name matching product usage. `advocacyTagBody` is an explicit four-field object rather than a
  spread of the draft, so a `level` field added to a form somewhere cannot ride along.
- **D-274 — There is no PATCH, and the person card keeps the two arrays separate.** A tag records
  that a thing happened on a date; editing the date or note afterwards would make the evidence note
  a mutable claim about an immutable event. And `advocacy_tags` sits beside `advocacy` on the card
  rather than merged into it — a single combined array is how the public one silently starts
  satisfying the internal gate. Tags are returned as records, never as a count: "three advocacy
  tags" is one step from an advocacy level, and the date and note are the load-bearing part.

## VISIBILITY-SPEC Slice 1 — decay and withholding on persisted copilot runs (2026-08-06)

The first slice of `VISIBILITY-SPEC.md`: a completed copilot answer stops being rendered as current
once it is past the evidence window for its scope. **No migration.** 807 backend tests (was 795),
263 frontend (was 256), lint exit 0, clean build. Six captures in `design-screenshots/visibility-slice-1/`.

- **D-251 — This slice was built on Zach's instruction "continue building with what's specc'ed out",
  not on a formal naming of `VISIBILITY-SPEC.md` into `CLAUDE.md`'s authority chain.** Recording the
  provenance exactly, because D-239 says a proposed root spec is a candidate and not a permission,
  and an entry that read "in force" would manufacture an approval that was never given. Everything
  in the named chain is built, so the instruction has no other referent; §10 of the spec names Slice 1
  first; the slice stores nothing and reverts in one commit. **Slices 2–6 are not started** and
  `SURFACE-USAGE-SPEC.md` is untouched, pending Zach's confirmation.
- **D-252 — Answer freshness is a query-time projection over `generated_at`, never a stored state.**
  `copilot_service.answer_freshness` computes it on every read; a schema-introspection test asserts
  no `freshness` / `withheld` / `threshold_days` / `age_days` / `is_stale` / `revealed` column on
  `copilot_runs` and no freshness or decay table. The same reason readiness is a projection: a stored
  "this is still current" is a second source of truth that can disagree with the date it came from,
  and it would disagree silently, in the direction of looking fresher.
- **D-253 — The window is a property of the run's scope, and the payload carries it so the refusal
  can name it.** `ANSWER_WINDOW_DAYS` is program 14 / account 30 / portfolio 45: a program-scoped
  answer describes work that moves weekly, a portfolio-scoped one a shape that moves quarterly. This
  is a coverage threshold, not a benchmark — it asserts nothing about whether a 40-day-old answer is
  good, only that we stop restating it as current. The sentence says "the 30-day evidence window"
  rather than "the threshold", which is why `threshold_days` rides on the wire.
- **D-254 — A past-window answer is withheld, not dimmed.** The server sets `answer_markdown` to
  `None`; the client collapses the prose behind an explicit control that names the date
  ("Show what was written on 2026-02-14") and re-reads with `?reveal=true`. A greyed paragraph is
  still a rendering of the claim and an operator reads it as the claim. Revealing changes nothing and
  regenerates nothing: `withheld` stays `true`, `revealed` becomes `true`, the age chip stays stale.
  The two are separate fields for that reason.
- **D-255 — The claims and sources block is assembled before the withholding and is never subject to
  it.** An operator handed a refusal needs the evidence that explains it; hiding the evidence with
  the prose leaves them holding an assertion they cannot check.
- **D-256 — The refusal reuses `sharedPlan.withheldSentence`, the same function and not a copy.**
  The server authors a lower-case clause completing "held back because …" and the view frames it
  unedited; a frontend test asserts identity against that function rather than a substring. Two
  frames are two places a refusal can be softened independently (D-153).
- **D-257 — A withheld answer cannot seed an internal draft; both draft endpoints 409 and reuse the
  server's own clause.** Copying the prose into a saved document would carry it forward without the
  refusal that came with it — the same failure one step removed. Before this the draft path would
  have silently received `answer_markdown=None`.
- **D-258 — Ageing a run in a test lifts `trg_copilot_run_answer_frozen` for one statement and
  restores it from `sqlite_master`'s own text.** A completed run is immutable and correctly so, which
  is why no application path can age one; reading the trigger's DDL back rather than keeping a copy
  in the fixture means a test cannot leave the invariant weaker than it found it, and the restore is
  asserted.

  the review's width is the wrong number to ask about. First `@container` use in the codebase.

## Account drop zone — Slice 4 built, milestones and the §17 measurement amendment (2026-08-06)

`("create", "milestone")` as the second proposal route, and the six drop-zone events §17 deferred.
**No migration.** 795 backend tests green, 256 frontend (27 and 11 new). The slice's shape came out
of one finding: §10 offered two routes to a new target and preferred the normalized one, and taking
that route turns out to need no schema change at all — which makes §19's "with its own migration"
estimate stale rather than merely conservative. Both specs now say so.

- **D-242 — The new target is a normalized pair with a NULL legacy name, and `_persist_run` learned
  to speak both vocabularies rather than one being converted.** `extractor.PROPOSAL_KINDS` is the
  *wire* vocabulary (`MUTATION_TYPES + ("create_milestone",)`); `MUTATION_TYPES` stays exactly the
  nine names migration 0043's CHECK accepts; `KIND_PAIRS` maps wire → `(intent, target_type)` and is
  built from `proposals.LEGACY_MUTATIONS` so the two sets meet in one place. A milestone proposal
  therefore stores `intent='create'`, `target_type='milestone'`, and `mutation_type` **NULL** — which
  is what 0043 made the column nullable *for*, and why the CHECK is untouched by this slice (a test
  asserts `"milestone"` appears nowhere in the `extraction_proposals` DDL). The consequence that
  matters is at dispatch: every place that read `mutation_type` to work out what to build now reads
  `target_type` directly, because stripping a `create_` prefix off NULL raises. §10 predicted that
  500; reading the normalized column closes it rather than dodging it. `_persist_run` accepts either
  shape — normalized keys when the caller speaks them, `legacy_pair(mutation_type)` when it does not
  — because five tests in `test_readiness_review_fixes.py` call it directly with legacy dicts, and
  the alternative was a second translation site, which is how two vocabularies drift.
- **D-243 — The two ways a milestone is undraftable produce different coverage entries, and
  `screen_undraftable` mutates the run's coverage in place.** A proposal with no date and one with
  no program are both refused, but a reader who cannot tell them apart cannot act: the first means
  "the document did not say when", the second means "tell me which program". Both sentences are
  authored on the server (`extractor._NO_DATE`, `_NO_PROGRAM`) and a test asserts identity with the
  constants rather than matching prose, because a view that composes any part of an "I did not do
  this" statement can soften one (D-153). The screen runs inside `_persist_run` and appends into the
  caller's `coverage` dict, which is the same object the drop-text path and the `.eml` path each
  hand to `_record` — so the receipt sees the omissions, and the transcript and manual-paste callers
  get them from the same change rather than three.
- **D-244 — A proposal may name a milestone and a date and nothing else.** `at_risk`,
  `completed_on`, `completion_note`, and `completed` are rejected at validation and again at accept
  time, so an override cannot smuggle one in after review. The rule is the readiness one one level
  down: a plan says *when* something was expected, readiness says whether it is true, and a document
  that could assert a milestone was completed would be a proposal asserting a state.
- **D-245 — The mock's milestone rule is appended last and fires on a cue, and `find_date` refuses
  more than it parses.** Appended last because `_RULES` matches in order and the commitment and
  decision cues are broader; cue-only because a rule that fired on any future-tense sentence would
  draft a milestone out of every plan mentioned in passing. `find_date` accepts ISO, `1 October
  2026`, and `October 1, 2026` — **no slash forms**, since `03/04/2026` is two different dates
  depending on who typed it, and returns `None` when a sentence carries two candidates rather than
  taking the first. A relative phrase ("end of next quarter") is not a date and drafts nothing.
  Both prompt versions were bumped (`cue-rules-2`, `structured-2`) because the extraction fingerprint
  includes them and a re-run under the old version would otherwise be treated as identical work.
- **D-246 — §17.3's sixteen events become twenty-two, and only one of the six carries a property.**
  An amendment to the existing allowlist rather than a second event store, because two contracts
  about what may leave a record eventually disagree. The property rule here is narrower than the
  surrounding events on purpose: **a filename is document content by another name**, so none of the
  six carries a filename, kind, size, byte count, or proposal count. `drop_refused` gets
  `reason_code`, and the code is the drop's own five-value `outcome` enum rather than a client
  vocabulary. `drop_no_proposals` gets none, though "HTML-only or all-quoted?" is the diagnostic
  somebody will want — there is no such code on the server, and the client deriving one by matching
  the operator's sentence would be a view reconstructing server semantics from prose the server
  authored. `kind` and `proposal_count` were considered and left out: they can be added at this
  review point later and they cannot be un-collected. Client-side refusals are counted with two
  codes (`too_many_files`, `unsupported_kind`) and deliberately not three — `screenFile` returns no
  sentence for an oversized file precisely so the server authors that refusal, which means the file
  *is* sent and returns as a `rejected_kind` receipt, and a third code would double-count it.
- **D-247 — The milestone review form edits the name, and there is no `_IDENTITY_FIELDS` entry.**
  `create:milestone` is the first target whose text field is not the default one, so `editableFields`
  now reads a `TEXT_FIELD` map with an explicit `null` for `update:person` instead of special-casing.
  The duplicate check is left with name-equality-within-program only: `_IDENTITY_FIELDS` requires two
  agreeing fields, and a milestone's only identity field beyond its name is `target_date`, so an
  entry there would name a check that can never fire — which reads as coverage that does not exist.

## Account drop zone — Slice 3 built, grounding + accept-all + duplicates (2026-08-06)

`app/proposal_grounding.py`, the §12 duplicate check in `app/intake_drop.py`, `run_id` on
`proposed_updates`, `POST /api/extraction/runs/{run_id}/accept-all`, and
`frontend/src/proposalGrounding.js` + the split view and bulk bar in `ProposalReview.jsx`. **No
migration** — `intake_drops.duplicate_of_id` already existed from 0052 and was simply unwritten.
Slice 3 improves every proposal, not only dropped ones: an extraction started from an interaction
gets the same split view and the same batch key. **767 backend tests green, 245 frontend** (25 and
16 of them new), clean build. Screenshots still blocked at the capture layer — see `HANDOFF.md`.

- **D-226 — Duplicate detection runs after the refusal and before any parse.** The only ordering
  that works in both directions. Put it first and a re-dropped PDF is answered "you dropped this
  before" — true, useless, and it hides the sentence that tells the operator what to actually do, so
  `rejected_kind` and `parse_failed` are deliberately outside the duplicable set. Put it later and
  the decode, segmentation, extraction, and ingestion all run to produce a second copy of records
  that already exist. `screen()` first, hash second, parse third.
- **D-227 — The duplicate receipt names the earlier drop, because silence is the actual bug.**
  Detecting the duplicate and returning an empty receipt would be correct and would still fail: from
  the operator's chair, silent dedupe and a failed upload are indistinguishable — a file was dropped
  and nothing appeared. The receipt states the date, the filename, and offers the earlier run's
  drafts. It carries the earlier drop's `comm_message_id` (identical bytes *are* the same message, so
  that is a read rather than a guess) but deliberately **not** its `extraction_run_id`, because
  reporting "drafted 6 updates" a second time is the double count §12 exists to stop.
- **D-228 — Earliest, live, account-scoped, and tie-broken on `rowid`.** Earliest so the chain never
  grows into something to walk; live only, because an archived drop has been withdrawn and pointing
  at a receipt the operator can no longer open is the dead end this feature exists to prevent;
  account-scoped because D-225 forbids a receipt from holding a handle on another account's record,
  and the same deck legitimately goes to two clients. `rowid` rather than `id` as the tie-break:
  timestamps are second-resolution and ids are random hex, so ordering by id picks an arbitrary
  member of that second and the "earliest" guarantee silently does not hold.
- **D-229 — A duplicate stores no second copy of the snapshot.** §5 lets an operator delete retained
  source text. A duplicate row with its own copy would leave an identical snapshot one row above the
  deleted one, and the deletion would not have been a deletion.
- **D-230 — Grounding never reconstructs the source from `interactions.raw_notes`.** It is sitting
  right there and it is the wrong answer twice: the run's `content_hash` is over the text handed to
  the extractor, so nothing links the two, and `raw_notes` is mutable afterwards. A run has a
  retained document **iff a drop points at it**; otherwise the pane says no source text was kept. A
  fabricated provenance claim is worse than a stated absence.
- **D-231 — Exactly two match strategies, and the second maps offsets back through an index.** Exact,
  then whitespace-normalized — a mail client rewraps lines, so refusing to see through whitespace
  would leave most real quotes unlocatable. Nothing fuzzier ships and there is no similarity
  threshold, because a highlight on nearly-the-quote presents different words as the ones the draft
  cited. Normalization keeps a per-character map to the original offsets so the marked slice is
  byte-identical to the span; a quote that cannot be found says so and marks nothing.
- **D-232 — Windowing is subtractive, so the server states it and re-bases the offsets.** A 1 MB
  snapshot is not a pane. The window is 3000 characters centred on the quote, the sentence naming
  what was shown of what total is authored on the server (D-153), and the location offsets are
  re-based onto the slice — offsets left in whole-document space would confidently mark text
  thousands of characters from the quote, which is the worst available outcome.
- **D-233 — Accept-all is a dry run of the accept path, in its order, all-or-nothing.** §11.4 names
  three guards; a fourth is unavoidable in practice — a proposal whose payload cannot satisfy the
  target schema (a commitment has no responsible party, internal owner, or due date an extractor can
  supply as ids). A batch that discovers its fourth item is unacceptable has already created three
  records nobody chose, and nothing on the screen says which three. So every item is checked before
  anything is written and the whole call 409s naming what blocked it.
- **D-234 — "Every item `proposed`" is read over the run's *open* items.** Reading it over every item
  would disable accept-all permanently after a single rejection — a rule that punishes reviewing,
  which is the act this surface exists to encourage.
- **D-235 — `run_id` is a filter on the one queue, and what it withholds is stated.** Same
  composition, same grouping, same command set — not a second queue. Manual capture belongs to an
  interaction rather than to a run, so there is no honest way to include it in a run's slice; it is
  withheld and counted. D-160's rule in the other direction: a response the server calls complete can
  still be subtractive, and a narrowed queue that looked like an empty account would be the worst
  version of this. A run id from another account is refused rather than returned empty.
- **D-236 — `bulk` is a property on `proposal_accepted`, not a separate event.** Each item in a batch
  genuinely *is* an acceptance, so a `proposals_accept_all` event would leave the acceptance funnel
  undercounting by however much the batch path is used. The bounded boolean is what lets a later
  reader separate the two without the counts disagreeing. `a` is added to the **existing** keydown
  handler; a second window-level listener is how two handlers start disagreeing about focus.
- **D-237 — The citation mark carries no hue.** `--bg-surface` over `--bg-sunken` gives lift in both
  themes, plus a rule and primary-ink weight — three redundant signals, none of them colour. Status
  hues are reserved for account condition and the accent belongs to interaction; a quote is neither,
  and a green highlight would read as "verified".
- **D-238 — Two bugs the tests found, both in existing code.** `proposed_updates` rebound its own
  `run_id` parameter as the loop variable, so after the loop it held the last run and every scope
  statement described a narrowing nobody asked for — including suppressing manual capture on an
  unfiltered read. And `prior_drop` ordered by `id`; see D-228.

## Account drop zone — Slice 2 built, `.eml` (2026-08-06)

`adapters.parse_eml_bytes`, `ingestion.DropOrigin`, migration 0053 (`email_file` kind +
`comm_message_id`), `association.pick_program`, and the `_process_eml` branch in `app/intake_drop.py`.
A dropped `.eml` now takes the **same** path a synced one does — `source_reference` → `comm_message`
with thread identity and `new_text_hash` → one extraction run over new text only — so the
correspondence-derived relationship-health counts cannot diverge by how the message arrived (§7.4).
742 backend tests green, 229 frontend (16 of them `intakeDrop`). Seven decisions, each a place the obvious implementation was
wrong rather than merely different.

- **D-219 — One ingestion path with an origin, not a second path for drops.** `ingest_email_message`
  now takes an optional `DropOrigin`, and the five things a drop changes are all facts about *origin*
  — the account the operator was looking at, its program, the provider, the source label, and which
  extractor backend and coverage the run carries. Everything else, including both dedupe checks, sits
  **outside** the branch. That placement is the whole point: dropping a message the mock inbox has
  already synced is a no-op *because* the duplicate check is shared, and a `.eml`-shaped copy of the
  function would have grown its own answer to "have we seen this?" within a slice.
- **D-220 — `read_whole_thread` is refused for `.eml`, not honoured and not ignored.** The toggle is
  right for a paste, which has no message identity and may genuinely be all new text. It is wrong for
  a `.eml`, whose quoted history is made of messages that each carry their own `Message-ID` — each is
  already a record or will be when it syncs, so reading them is the duplicate-proposal storm §14.8
  exists to prevent. It lands in `coverage.refused` with a server-authored reason, and the test
  asserts the *behaviour* changed (the span in the quoted history produces no proposal), not that a
  label appeared.
- **D-221 — A `.eml` with no sender is `parse_failed`, not an empty message.**
  `email.message_from_bytes` never raises: hand it a plain text file and it returns a message with no
  headers whose body is the whole file. Guarding on "no subject *and* no body *and* no sender" let a
  renamed `notes.txt` through, which would have minted a `comm_message` with an empty `from_addr` and
  `direction: inbound` — a correspondence record with nobody on the other end, quietly skewing the
  exact reciprocity counts §7.4 protects. The guard is `from_addr` alone, because a sender is the one
  header this path cannot do without.
- **D-222 — The content hash decodes with `latin-1`.** Not a claim about the encoding — it is the one
  codec that maps every byte to a distinct character, so the hash stays injective over byte strings.
  `utf-8` with `errors="replace"` collapses every undecodable byte to the same character, so two
  different non-UTF-8 messages would hash identically and the second would be reported a duplicate
  and never read. Live risk precisely here: the messages worth reading are the ones with a declared
  non-UTF-8 charset.
- **D-223 — `pick_program` is constrained to the account.** Promoting `_pick_program` for the drop
  path exposed a real hole rather than a hypothetical one: it picked the most recent stakeholder role
  for the matched people with no account constraint, so a person holding a role in *another* account's
  program would put this client's material under that client's program. Unreachable while the account
  was inferred from the same people; reachable the moment a caller supplies the account independently,
  which is exactly what a drop does. The JOIN to `programs` is load-bearing, and a test asserts it.
- **D-224 — `email_file` is a distinct kind, and `.msg` gets its own refusal.** Reusing `email_paste`
  would make `comm_message_id IS NULL` mean two different things — "a paste carries no Message-ID" and
  "an `.eml` failed to parse" — and the receipt would have to guess which. Migration 0053 is a CHECK
  widening on a table rebuild, no data reinterpreted. Separately, `.msg` left the `.eml` refusal alias
  loop: it is a Microsoft compound binary, not RFC-822, so "email files aren't read yet" would now be
  both false and unhelpful.
- **D-225 — A duplicate found on another account is named but not linked to; HTML-only is still
  correspondence.** Two ways the receipt tells the truth without overreaching. When the message is
  already recorded under a different account the receipt says so and leaves `comm_message_id` NULL —
  a receipt in this account must not hold a handle on another client's record, and re-scoping is the
  operator's act. When a message has only an HTML part the `comm_message` is still created and only
  extraction is skipped, because declining to read markup is a fact about our parser, not about
  whether the correspondence happened; `_body` returns a `body_source` (`text/plain` / `html_only` /
  `empty`) so the receipt can say which of those it was instead of showing one silent blank.

## Account drop zone — Slice 1 built (2026-08-06)

Migration 0052 (`intake_drops`), `app/intake_kind.py`, `app/intake_drop.py`,
`app/routers/intake_drops.py`, `src/intakeDrop.js`, `src/views/AccountIntakeDrop.jsx`, and
`document_drop_intake` in `CONNECTIONS.md`. Drop or paste on the Operate lens → screen → detect
kind → parse from bytes → the **existing** extractor → `_persist_run` → the **existing**
`ProposalReview`. 33 backend tests, 12 frontend. Five decisions departed from the spec's own §15/§19
and each is here rather than in a commit message.

- **D-214 — Base64 in a JSON body, not `multipart/form-data`.** The spec assumed an upload. There is
  no `UploadFile` anywhere in this codebase and `python-multipart` is not installed, so multipart
  would add a dependency to the one feature whose whole argument is that it reuses what exists.
  Base64 also *preserves* D-211's ordering — the endpoint receives bytes, so screening and kind
  detection still happen before any decode, and Slice 2's `.eml` can decode per MIME part. The 33%
  inflation is irrelevant against a 1 MB cap.
- **D-215 — Synchronous, not through the job table.** CLAUDE.md sends long-running work to the job
  table, and `run_extraction` is the work in question — but it is already synchronous with every
  backend it supports, so routing a drop around it would make the drop path behave differently from
  the path it delegates to. If a real LLM backend is ever wired in, both move together; splitting
  them now would mean two answers to "did this finish?" for the same call.
- **D-216 — The slice seam moved: Slice 1 is every text kind, Slice 2 is `.eml` alone.** The spec
  put transcripts and threads in Slice 2. Cue-stripping is ten lines of regex and quoted-thread
  splitting is `email_thread.split_quoted`, which already exists and is already tested — so the
  original seam deferred the user's *stated primary case* (a pasted email thread) behind almost no
  work, while shipping a Slice 1 that reads the whole quoted history and duplicates every proposal
  once per reply. What is genuinely expensive is D-212: refactoring `_parse_eml` and creating a
  `comm_message` through `ingestion.ingest_email_message`. That is now all of Slice 2, and a dropped
  `.eml` refuses in Slice 1 **with its own named reason** rather than the generic one — "not yet,
  paste the text meanwhile" is a different sentence from "we don't take that".
- **D-217 — Coverage is a `_persist_run` keyword, not a second table.** Per D-213 the run owns its
  coverage; the only missing piece was a way to hand it in at insert time. One optional kwarg
  writing to the existing `extraction_runs.coverage_json` beats a drop-side copy that could drift.
- **D-218 — `named_not_proposed` and `refused` ship as honestly empty lists.** Populating them needs
  entity recognition the app does not have. An empty list is a true statement about a coverage
  dimension we cannot yet measure; a fabricated "2 people named, not proposed" would be a coverage
  claim about material that was never identified, which is the exact failure §14 exists to prevent.
  `skipped` is real from day one because quoted-history and cue characters are counted, not guessed.

## Account drop zone — the review revision (2026-08-06)

An adversarial review traced every "reuse this, unchanged" claim in `ACCOUNT-INTAKE-SPEC.md` into
the code. Ten findings, all verified against file and line, all folded in; `ACCOUNT-INTAKE-SPEC.md`
§22 records the full disposition. Four of them changed the design rather than the wording.

- **D-210 — The drop receipt resolves nothing.** The first draft gave the receipt per-item accept /
  reject / resolve controls and its own keyboard map. That is a second review surface, which
  `ProposalPreview.jsx:1-14` and `ProposalReview.jsx:1-20` already ruled out in their own words —
  two surfaces that both resolve proposals would eventually disagree about what a command means. The
  receipt is now an outcome line and a link; grounding (the span-and-snapshot split view, which is
  the genuinely new idea) lands *inside* `ProposalReview`, where it benefits every proposal rather
  than only dropped ones. The per-item bare `a` is withdrawn for the same reason —
  `ProposalReview.jsx:364-365` states that accepting is deliberately not a bare keystroke because it
  needs the required fields, the matches, and the conflict in view first. Accept-all (D-208)
  survives that comment because its three guards *are* those conditions, but it lands in
  `ProposalReview` scoped to one run, not in a second window-level handler.
- **D-211 — Decoding happens inside the per-kind parse, not before it.** The first draft decoded
  bytes to `str` at step 2 and handed text to every parser. `adapters._parse_eml` reads bytes on
  purpose, with a comment saying so, because MIME parts declare their own charset — decoding an
  `.eml` as UTF-8 first corrupts exactly the messages most worth reading. The pipeline now screens,
  detects, then parses **from bytes**, per kind. Decodability is a per-kind precondition, not a
  global one. This does not weaken D-206: "text in, bytes never stored" was always about
  *persistence* — the bytes exist in memory for the length of the request either way, and the rule
  is that nothing binary reaches disk.
- **D-212 — A dropped `.eml` goes through `ingestion.ingest_email_message`, not around it.**
  Treating it as "just another text kind" would produce proposals but no `source_reference` and no
  `comm_message` — so the message would be invisible to the comms timeline and, worse, absent from
  the correspondence-derived relationship-health counts, which are counts over our own
  correspondence and are wrong when correspondence is missing. A silently under-counted signal is a
  worse failure than a refused file. Pasted email *text* carries no Message-ID, so it creates no
  `comm_message` and says so in `coverage.skipped` rather than pretending.
- **D-213 — `intake_drops` stores only what `extraction_runs` does not.** The first draft carried
  `coverage_json` and duplicated run fields; migration 0043 widened `extraction_runs` precisely so
  there would be one place for a run's coverage and error state, and a second copy is the cached
  disagreement that rule exists to prevent. The table keeps the drop-specific facts — filename,
  detected kind, byte length, the text snapshot and its deletion stamps, the new/quoted character
  split, the outcome, and the foreign keys to the run and the `comm_message`. `outcome` is the
  single exemption in the forbidden-column introspection test and is asserted by name; `coverage` is
  prohibited outright.

Also resized rather than redesigned: `("create","milestone")` (D-207) is six changes across five
modules plus a migration, not a one-line allowlist edit, and moves to Slice 4; the six telemetry
events break two literal assertions and are a contract amendment to `ACCOUNT-PATH-SPEC.md` §17.3
rather than an addition; `source_version_key` is written and displayed but never queried, so
duplicate detection is new code; and `intake.parse_intake`'s outputs share nothing with
`extractor.MUTATION_TYPES`. One finding was answered with a distinction rather than accepted:
`ProposalPreview` sits below `ReadinessSummary` because a draft nobody has accepted is not an
account condition — that reason governs the **output**, not the **input**, and a capture surface
buried in the right rail fails the 30-second rule. The zone is prominent; its results are not.

## Account drop zone — the four intake calls (2026-08-06)

`ACCOUNT-INTAKE-SPEC.md` (Stage 16, additive) was written against Zach's ask for "a nice pretty
place where I can drop files … parse it and update the corresponding trackers". Four calls were put
to him; all four went the way the spec recommended. Nothing is built yet.

- **D-206 — PDF, DOCX, images and audio are refused by name with a stated reason, not silently
  ignored, and the reason is a governance fact rather than a capability gap.** A dropped file is the
  first material of arbitrary origin, chosen at runtime, to enter this installation — everything
  before it was a fixture we wrote. So the rule is **text in, bytes never stored**: decode in memory,
  persist the text on `intake_drops.snapshot_text`, discard the bytes when the request ends, nothing
  on disk outside SQLite. A `.txt` is text already; a PDF is a container, and reading one means
  either holding the file (`file_storage`, unopened) or running a text-extraction library over
  untrusted binary, which is parser hardening nobody has reviewed. Both are the data-handling
  conversation. The refusal therefore names the reason and offers the working path ("open it and
  paste the text") — "unsupported file type" would teach the operator the product is limited, when
  the truth is that one boundary is closed and the alternative takes four seconds. Reopens when
  `file_storage` opens.
- **D-207 — `("create","milestone")` is added to `TARGET_ALLOWLIST`, with the program required and
  no date ever drafted from a relative phrase.** A dated event is the most valuable thing in a
  dropped kickoff note and the only thing that feeds the launch timeline; without it "what did the
  onboarding call tell us" cannot include a date. `intake.accept_proposal` already creates
  milestones through `repo.insert`, so the audited native write path the proposal contract requires
  already exists — only the allowlist pair and a payload schema are missing. Two constraints ride
  with it because a milestone is the first proposable target carrying a date the rest of the app
  plans against: `program_id` comes from the operator's selector and is never read from the text (a
  homeless date has nothing to sit on, so it is reported in `coverage.refused` instead), and
  `target_date` must be unambiguous — "some time in the autumn" produces a `named_not_proposed`
  entry, because a guessed day becomes a day the operator then works to.
- **D-208 — Accept-all is one keystroke, and its three guards are the decision rather than
  decoration.** Enabled only when every item in the drop is `proposed` with no conflict and no match
  candidate; an explicit act on a visible list; and implemented as a loop over the per-item native
  accept path so each acceptance writes its own audit row. Never triggered by confidence, never a
  default. The point of the drop is that the gap between "it parsed my file" and "my trackers are
  updated" costs about two seconds — but a batch action that could fire over something unresolved
  would be the threshold auto-apply the spec rejects, wearing different clothes.
- **D-209 — A source snapshot is kept until explicitly deleted; no timer, no expiry on resolution.**
  Grounding is where review speed comes from, and a snapshot is the evidence behind a citation that
  outlives the review — a commitment accepted in August is read in November by someone asking what
  was actually said. **Delete source text** nulls the column while keeping the drop, its hash, its
  coverage and every proposal drawn from it; the span still renders above a line saying when the
  source was deleted. A timer that silently destroyed the evidence behind a live proposal would be
  strictly worse than keeping it, and auto-deleting on resolution would delete it exactly when the
  record starts being read by someone who was not there.
- **Not actioned yet: the `document_drop_intake` row in `CONNECTIONS.md` lands with Slice 1.** Its
  content is settled (local, text-only, original bytes never persisted, no adapter, no network
  path), but every row in that registry today describes a boundary with code behind it. A row for a
  feature that does not exist would be the file's first aspirational entry, and the registry is only
  useful if reading it tells you what the installation actually does.

Zach: "Review the account plan surface build please - poke holes where needed", then "make the

traced, found unreachable through any current route, and are recorded at the end rather than
patched.

- **D-196 — The plan list and the plan picker answer different questions, and reading the second
  off the first made the write unreachable.** `list_plans` returns an account-wide plan inside a

## The launch timeline (2026-08-05)

Zach: "There will always be some kind of timeline we're working with — can we look up best
practices for how to show this in a visually appealing way?" and, when asked where it should live,
"Plan tab, primary". Best practice was read first (UX Patterns' timeline anatomy, Eleken, Lucen,
Slickplan) and the rules that survived contact with this codebase are recorded in the module
docstring; the ones that changed a decision are below.

- **D-189 — Three swim lanes against one axis, not one merged stream.** The anatomy's "hybrid"
  variant — chronology plus accountability — is the one that fits, because migration 0051's whole
  point is that the three kinds answer different questions. A single stream would need one status
  vocabulary for all 23 things, and the weakest of the three always wins that merge. Lanes share
  the axis and nothing else: `pointStatus` reports a setup step as done/open, a condition in
  readiness' own state and freshness words, and a milestone in the status an operator recorded.

- **D-190 — Shape codes the kind; colour is spent only on the two flags that must never be
  colour-alone.** Square, circle, diamond, named in the legend and in every marker's accessible
  name. Status hue appears on exactly two marker forms — overdue and flagged-at-risk — and both
  also gain a ring, so the difference survives greyscale and a colour-vision difference. The
  guarantee is testable rather than conventional: `markerLabel` composes the accessible name in the
  module, and a test asserts every marker's name ends with its status words. A view that assembled
  its own label could omit the status half.

- **D-191 — Rendering found a defect no test could: coincident dates drew markers on top of each
  other.** A launch anchored to a kickoff puts five setup steps on day zero, and one marker per row
  meant the lane said seven and showed three — a timeline silently hiding rows, which is the same
  failure as dropping them. `clusterPoints` groups a lane by date into one marker carrying a count,
  and the caption discloses every member. A cluster is `done` only when **all** its members are:
  `some` would let three ticked rows hide the one that is open. This is the **eighth** consecutive
  slice where rendering the surface found something 200 green tests could not.

- **D-192 — The axis is bounded and says what the bounds cost.** 45 days back, 120 forward, always
  containing today; anything outside is counted in `window.clipped` and stated in one sentence the
  module authors whole (D-153's rule: a view that composes half of a subtractive notice can drop
  the other half). Unbounded would let one abandoned milestone squeeze this quarter into a few
  pixels. The notice carries no status word — a row the axis cannot place is not a failure.

- **D-193 — The timeline computes no state and invents no duration.** Every readiness axis is
  passed through untouched; the one thing derived is `late`, a comparison against a date the plan
  already states, and it is said *beside* a reading rather than instead of one — an overdue
  condition reading `thin` reports "thin, stale, overdue". Points, never bars: all 23 things are
  moments, and a bar from "now" to a due date would assert a start nobody recorded.

- **D-194 — One detail surface, not two.** Selecting a marker fills a caption; a condition's
  caption offers the way through to the same requirement panel the stage cards open. The timeline

## Account Path Slice 6 — shared plans and generated outputs (2026-08-05)

## Account Path Slice 5 — evidence, relationships, and governed advancement (2026-08-05)

- **D-149 — A link is a relationship and never a state, and migration 0046 is shaped so it cannot become one.** Slice 5 adds four link tables — `readiness_requirement_action_links`, `requirement_evidence_links`, `milestone_action_links`, `gate_requirement_links` — and not one of them has a `state`, `status`, `met`, `freshness`, or `coverage` column. Closing a linked Task settles the Task; the condition remains whatever the records say it is on the next read. This is the same rule D-139 and D-143 already enforce one level up, applied to the layer that is most tempting to break: a link table is exactly where somebody would cache "this requirement is satisfied" to avoid re-evaluating, and the cached copy would then disagree with readiness the moment the underlying record changed. `RequirementLinks` says so in the UI too — "A closed action stays listed. Closing settles the action; the condition is still whatever the records say it is."
- **`blocked` and `insufficient_data` are different verdicts, and telling them apart required a real bug fix, not just copy.** `advancementVerdict()` returns `blocked` only for conditions that were *evaluated and are not satisfied*, and `insufficient_data` where something could not be evaluated at all. Two things had to change for that distinction to be true rather than aspirational. First, `readiness.evaluate` **pops** each pillar's `coverage_failures` as it aggregates them into the top-level `result["coverage"]["failed_evaluators"]`, so `phase_readiness`'s per-pillar read found nothing every time and every gate reported `coverage: complete` no matter how many evaluators were unreadable; it now reads the response's own coverage block. Second, `playbooks._readiness_readings` never carried `evaluator_key`/`evaluator_version` onto a component, so a caller could not tell "unsatisfied" from "unreadable" even with the failures in hand — the component is the only place that knows which evaluator produced a state, and it now carries the identity verbatim. The failure mode this closes is the carried-forward-good-state one in reverse: a gap nobody could measure reading as a gap somebody could go close.
- **An override is offered, is never the default, and is described by what it does not do.** `overrideConsequences()` enumerates three risk-toned consequences in the operator's words — the gap "does not fill it", the gate "stays open", and "No readiness state changes" — and the checkbox is unchecked with the normal advance as the primary button. The dialog then lists the exact conditions the override accepts, snapshotted, and the history row keeps a standing left rule so an override is findable months later rather than only badged. Every phase the transition route accepts is offered as a labelled option (`phase_options`), because a non-adjacent move that is only reachable by hand-posting is a hidden capability, not a guardrail.
- **The advance is checked against the answer that was read, not against a fresh one.** `PhaseAdvanceDialog` sends `readiness_stamp` from the payload it rendered. Readiness is recomputed on every read, so between opening the dialog and confirming it, a condition can change; advancing against a state nobody saw is the same class of error as `expected_target_updated_at` guards on the proposal path (D-147).
- **No generic-evaluator requirement definitions were seeded, and the omission is deliberate.** A pillar's `requirements` list includes every live definition, so seeding one in a migration would assert a new readiness condition against every account in the database — a product decision about what teams are now required to have, dressed as an implementation detail. The tests author their own definitions instead. Slice 5's link and evidence tables work against whatever definitions exist; they do not need a seeded one to be exercised.
- **There is one waive command.** `delivery.py` delegates to `phase_readiness.waive_gate` rather than carrying its own copy. Two waive paths that could diverge on what a waiver records is the same second-source-of-truth defect as a stored state, one level down.
- **`Unblocks the Launch gate` is computed once, on the server, and the client's second implementation was removed.** `execution_path._gate_impact` already narrows three ways — the relation must be `advances`, the gate must still be `open`, and it must gate the program's *current* phase — and appends the clause to the candidate's `reason` with `coverage.omitted_sources` naming itself on failure. A `MoveUnblocks` component that re-derived the same claim per move (an N+1 fetch, and reading a `focus.id` that `_target` does not emit) could disagree with the sentence directly above it. `pathLinks.unblocksReason` survives for the *action detail*, which has no reason string to append to; the ranked queue does not use it.
- **The create-action form links what it creates, and reports the link separately from the record.** `RequirementDetail`'s form writes the Task or Commitment, then posts the `advances` link; if the link fails the toast says "Created, but the link failed" rather than claiming a relationship that does not exist. A requirement with no plan instance shows no link section at all — an unscheduled condition has nothing for a link table to key on, and an empty section would read as "nothing is linked yet".
- **The gate band renders only in single-program scope.** An account with several programs has several gates; picking one to show would be an arbitrary answer to a question the reader did not ask.
- **Timeline dependencies are a secondary band under the chart, not lines drawn across it.** §15.2 allows only explicit relations, and a line drawn between two dated markers is read as a dependency whether or not one was recorded. A milestone with no accepted relation draws nothing — the absence of a line is the absence of a recorded dependency, not a rendering gap. `.path-dep-rule` is never a status hue for the same reason: a recorded relation is not a state.

## Account Path Slice 4 — transcript/email proposals and the one review surface (2026-08-05)

- **D-148 — There is exactly one place in the app where a proposal is decided, and the legacy enum that made a second one possible is gone from the frontend.** `ProposalReview.jsx` is now the only surface that accepts, rejects, resolves, or supersedes; the Overview card and the Extraction screen both open it rather than each carrying a shallower copy. `Extraction.jsx` kept its ingest half and lost `ProposalRow` — the last frontend reader of `mutation_type`. The point is not tidiness: that enum can only describe *creations*, so the Extraction screen physically could not offer `update:person` or `use existing`, and the same proposal meant different things depending on where you reached it. Two surfaces that both resolve proposals will eventually disagree about what a command means, and the disagreement is invisible until someone acts on the weaker one.
- **A command is offered only when it can succeed, and the reason it cannot is part of the accessible name.** `commandsFor()` returns `{enabled, why}` per command and the button carries `aria-describedby` pointing at the rendered reason — "Needs Responsible party, Internal owner, Due date", "Pick the record that already holds this", "No other proposal covers this material". The alternative shipping pattern is a live button that 422s; that teaches the operator to distrust the surface. Nothing is preselected and nothing is ordered by model confidence, per the copilot rule that a numeric confidence badge is prohibited — the reviewer's evidence is the source span and the match candidates, not a score.
- **Editing the draft renames the command.** An untouched proposal offers `Accept as drafted`; the moment any field differs it becomes `Apply my edits`, and the accept revalidates the *edited* payload rather than the drafted one. Applying an edit under a label that says "as drafted" is how an operator ends up certain they accepted what the source said.
- **An empty optional field is omitted from the overrides, never sent as an empty string.** An empty string is a value: sending one erases the drafted title rather than leaving it alone. `overridesFrom()` drops empties; required fields are checked separately and block the command instead.
- **Supersede got a control rather than staying an advertised command with nothing behind it.** The picker offers only *open proposals over the same target type from the same run*, because superseding across target types would close a task against a risk, and across runs it would let one source's reading silently retire another's. Where no sibling qualifies the command says so.
- **The decision rules are a pure module, and the component holds no policy.** `proposalReview.js` (19 tests) decides what is editable, what is required, what the overrides are, and which commands are live; `ProposalReview.jsx` renders them. This is the only way the rules are testable at all — the frontend harness is `node --test` over pure modules with no renderer and no jsdom, so anything expressed as JSX is untested by construction. Corollary worth stating because it bit this slice: a green frontend suite is not evidence that a surface renders, and every real defect here was found by loading the app, not by the tests.
- **Applying a proposal must not eject the reviewer from the queue, so the parent is told at close time, not at decision time.** `ProposalPreview` holds an `appliedWhileOpen` ref and fires `onApplied` from the slide-over's `onClose`. Reporting each decision upward immediately is correct data-wise and wrong workflow-wise: it bumps the account's `reloadKey`, and `AccountCommandCenter` blanks itself to a loading state while it refetches — unmounting the card and the open slide-over with it. Hoisting the `SlideOver` out of the card's own early returns was necessary but not sufficient; the unmount was one level up. The card's own pending count still refreshes on each decision through its local `tick`, so the queue drains visibly while the account refresh waits for the operator to finish.
- **The extraction boundary for an email is its new text, and the content hash is a hash of that.** `email_thread.py`'s `split_quoted` takes everything above the first quote boundary; `0045` stores thread identity from the `References` root, never the subject. Without this, a five-message thread is read five times and the same commitment is drafted five times. Deduplicating the proposals afterwards *cannot* fix it, which is the part that looks wrong until you check: two readings of one sentence in different messages carry different source references, locators, and span offsets, so they fingerprint apart — correctly. The duplication has to be prevented where the material is chosen. Attachments are referenced by name and never read, and an email whose account association is unresolved proposes nothing until an operator confirms it.

Two environment facts are recorded so the next session does not misread them as defects: flipping `data-theme` imperatively does *not* fully recompute styles in the headless engine (var-driven colours went stale while background colours flipped, which is what produced a false dark-theme contrast failure on `.btn.ghost`), so audit a theme by reloading into it; and `:focus-visible` never matches there because the offscreen window holds no focus, so focus-ring checks by that route are inconclusive. ## Adversarial review of RR-0/RR-1/RR-2 and the Account Path (2026-08-05)

- **D-147 — Seven defects the 513-test suite passed, all of them a claim the data did not support.** An external review read the readiness projection, the proposal store, and Slice 3's plan layer against their specs. Every finding it raised was reproduced first as a failing test and only then fixed; the file is `tests/test_readiness_review_fixes.py` (13 tests), and the common shape is worth naming — none of these was a crash, each was the app stating something confidently that its own records did not entail. Full suite 526 green; frontend 55 tests, lint, and the production build pass.
- **An account-scoped pillar is one fact, so its evidence can never be filtered by the program you happen to be looking at.** `evaluate()` built a single `_Ctx` per run and used its `program_id` for both scope selection *and* evidence loading, so `budget_owner` — explicitly account-scoped — read `met` on the account view and `unknown` inside a program whose records happened not to hold the evidence. `RELATIONSHIP-READINESS-SPEC.md` §4 already settles the applicability half (account scope takes the strongest applicability across live programs); the evidence half had the same requirement and did not have the code. `run(..., account_wide_evidence=True)` now separates the two: the scope program still decides phase and applicability, and evidence loads unbounded. Program-scoped pillars are untouched and a test asserts they still differ per program, because merging *those* would be the opposite defect.
- **A date in the future is stale, not current.** `_freshness()` compared `age <= window_days` with no floor, so a meeting recorded for 2099 produced a negative age, passed the window, and asserted a condition true *today*. The window is the interval ending at `as_of`; a date past the end of it falls outside exactly as an ancient one does. Two evaluators were loading those rows in the first place — `_engaged_people` and `_program_advocacy` had no `occurred_on <= as_of` bound — so a scheduled future meeting counted as engagement that had already happened. Both now bound on `as_of`, and the freshness floor is the backstop for any evaluator that forgets.
- **A governance preview that can only report "nothing changes" is worse than no preview.** `preview_definition_upgrade()` evaluated the current definitions twice and diffed the result against itself; it could not have shown a transition if one existed. The candidate evaluator version is now plumbed through `evaluate(..., evaluator_override=...)` and both sides genuinely run. Note the honest limit, since it will mislead a future reader otherwise: `_PILLAR_EVALUATORS` is a registry **gate**, not a dispatch table — dispatch does not vary by version — so with only v1 evaluators registered no *allowlisted* candidate produces a different answer yet. The test therefore asserts the override plumbing directly (an unregistered version fails closed to `unknown` and lands in `coverage.failed_evaluators`) rather than asserting a transition the registry cannot yet produce.
- **§6.7's optimistic concurrency was unreachable in the running app.** `expected_target_updated_at` was written by no production path and `target_id` was never stamped on a drafted proposal, so `conflict_preview()` returned `None` for every proposal the extractor produced and the one enabled update path — the placeholder fill — patched whatever it found. The extractor now stamps both at draft time (`_drafted_target`), and accepting a fill whose target moved since drafting returns 409 `stale_proposal` with the conflict rather than silently overwriting. `updated_at` is second-precision, so a sub-second race is still undetectable; that is a clock limit, and the defect was that the version was never compared at all.
- **Overrides on accept are operator edits, not a way to re-point a proposal at another account.** `accept_proposal` merged the caller's payload over the drafted one and passed `account_id`/`program_id` straight through, so a proposal drafted in one account could be written into another — the trust-boundary breach `match_candidates()` already fails closed against on the read side. `_require_scope_of_run()` now rejects a foreign account, an unknown or foreign program, and a program override that differs from the run's program, with 422 before any write.
- **Idempotency is scoped, or it closes one program's proposal against another program's record.** `already_resolved()` matched on fingerprint alone, so the same extraction accepted in two programs resolved the second against the first's target and reported `resolved_existing` for a record that program never had. The lookup now carries `AND r.program_id IS ?`. Repeat acceptance inside one scope still returns the existing target, which is the rule §6.6 actually states.
- **Migration 0044 closes the reverse direction of 0041's guard.** 0041 blocks writing a live requirement definition against a retired pillar version; nothing blocked the identical illegal pair arriving from the other side — retiring a pillar version that still has live requirements hanging off it. The resulting rows are exactly the state 0041 exists to prevent, and a one-directional guard reads as protection while leaving the easier path open. Retiring a pillar is now an explicit two-step.
- **The false claim in a verification document is a defect, and the fix is the correction, not a quieter sentence.** `design-screenshots/stage-15/VERIFICATION.md` said each `met` component *links* the records that decided it. It does not — `Readiness.jsx` renders plain `<li>` items and `Add evidence` opens the generic Ledger. The bullet now says "names", and a dated correction paragraph states plainly that §5.3's drill-through to the native record is unbuilt and that the claim was wrong, not the capture. The drill-through itself is a feature and stays on the list; deleting the sentence and shipping would have left the record saying the work was verified. The compact card's empty state was corrected the same way — it pointed at an affordance that branch never renders.
- **`api.persons` is the roster endpoint; the account's people list is not.** `RequirementDetail`'s create-action form read owners from the account detail, which by construction contains no internal colleagues (they are global records with a null `account_id`), so the internal-owner select was permanently empty while a commitment cannot be saved without one. It now fetches the account and the roster together, behind a liveness flag so a fast tab switch cannot set state on an unmounted form.
- **Two findings were left open as product decisions, not fixed silently.** The Operate lens renders a readiness card in both the sidebar and the main column, and the combined review's `View all` target is arguably the wrong surface. Both are judgement calls about what an operator should see, not defects in what the code claims, so they are Zach's to make.

Revisit if an adapter ever reads a source with its own lag.

## Stage 15 RR-2 — canonical proposal widening (2026-08-05)

- **D-145 — RR-2 widened the two proposal tables that already existed and added no third store.** `RELATIONSHIP-READINESS-SPEC.md` §6.1 settles the shape before any column exists: widen `extraction_runs` and `extraction_proposals`, do not add parallel `intake_runs`/`intake_items`, and do not hang proposal payloads off `capture_inbox_items`. Migration 0043 therefore creates **no new table** — every column lands on one of the two that already hold proposals. The split that does the work is `intent` (§6.2) from `target_type` (§6.3): the old `mutation_type` fused the verb and the noun into one enum, which is why it could only ever create — "correct this Task's owner" would have meant inventing `update_task_owner`, then one enum value per field forever. `mutation_type` stays populated because §6.5 requires the legacy contract readable until every reader is normalized, and `Extraction.jsx` still is not. `created_object_type`/`created_object_id` became `resolved_target_*`, because "created" is a lie for an `update`, a `resolved_existing`, or a `no_change`, and with exactly two readers this was the last cheap moment to rename it. 20 tests in `tests/test_rr2_proposals.py`.
- **`intent` gets a SQL CHECK; `target_type` deliberately does not.** The intent vocabulary is closed at five values by the specification. The target allowlist is not — §6.3 grows it and Account Path Slice 5 adds link/close targets — so it lives in `app/proposals.py` next to the native write path that must exist for a target to be legal at all. A row *configures* an allowlisted target and can never *create* one, the same rule migration 0041 applies to readiness evaluators. A CHECK here would let a migration widen the allowlist without a write path behind it. The allowlist is also a **pair**, not two lists: `(intent, target_type)` is permitted together or not at all, because a target that can be created is not thereby updatable — an update needs an audited patch path *and* a field allowlist, and most targets have neither. `link` and `close` are in the vocabulary and in the CHECK but disabled in Python until Slice 5's typed relationship and governed closure contracts exist; the vocabulary is fixed by the spec, the enabled subset is not.
- **No proposal may assert a readiness state.** There is no `pillar`, `requirement_key`, `state`, `composite_status`, or `phase` column, and `target_type` cannot name one because the Python allowlist omits every readiness target. Readiness is a query-time projection (D-139); a proposal that could write one would fabricate evidence. `FORBIDDEN_FIELDS` enforces the payload half in code rather than leaving it to review, because the field a proposal would need is exactly the one somebody adds for convenience.
- **Counts are derived, never stored — on the run and in the read model.** §6.5 suggests counts on `extraction_runs`; they are not there, and `proposal_read.py` recomputes them on every call. A stored `proposal_count`/`accepted_count` drifts from the rows it counts the moment one is resolved outside the counter's path — the second-source-of-truth defect D-141 and D-143 already rejected one level up. `error_json` and `coverage_json` *do* land, because an adapter's own failure report is a fact it observed and nothing downstream can recompute it.
- **Two identities, not one, both as plain columns.** §6.6: `external_id` alone is insufficient, because a provider item can be corrected, retranscribed, or reprocessed with a new extractor. The run carries a source-version identity (provider + external id + content hash + source kind) and each proposal a fingerprint over normalized intent, target, payload, span/locator, and extractor version. An identity table would have been the second persistence model §6.1 forbids.
- **One duplicate check is enforcement; every other is a suggestion.** §6.6 requires repeated acceptance to return the existing resolved target or a stable conflict and never create a duplicate, so `already_resolved()` is binding on the accept path. `match_candidates()` is not: §6.7's closing line makes possible matches suggestions, so it returns rows for a human and never blocks, merges, or re-ranks. A near-match that silently swallowed a proposal would lose work the operator never saw. Matching **fails closed on scope**: several execution tables carry only `program_id`, so a run with no program cannot be bounded to one account and returns no candidates rather than widening the search — a cross-account match is a trust-boundary breach and no amount of usefulness offsets it.
- **D-146 — The combined review is a read-model composition, and the tempting shortcut was never an INSERT.** §0.5 forbids `capture_inbox_items` becoming a second copy of extraction proposals, and the realistic way to violate that is not a migration — it is a merged response shape that flattens both stores into one row type, which then needs a stored copy to keep the vocabularies aligned. `app/proposal_read.py` composes at query time and writes nothing (a test counts rows in `capture_inbox_items` across the whole flow). Each side keeps its own `kind`, its own status vocabulary (`untriaged` is never restated as `proposed`), and its own command set (`convert`/`dismiss` versus `accept`/`edit_and_accept`/`reject`/`use_existing`/`supersede`) — a reader who could not tell them apart could not tell which command applies, so `frontend/src/proposalPreview.js` preserves the distinction and a hand-typed note is never dressed as cited. Grouping is by **run**, not interaction: a retranscription is a different source with a different content hash, and merging the two would attribute one extractor's drafts to another's reading. The program filter uses `AND program_id = ?` rather than an `IS NULL` fallback, because a null-program run is account-level work, not work in every program. 19 tests in `tests/test_rr2_read_model.py`; full suite 513 green, frontend 55 green.
- **The Overview card offers no accept or reject control, and the "latest" source is the latest with work left.** §8.1 caps the preview at three; a decision needs the match candidates and the conflict preview beside it, and those live on the review surface where there is room to read them, so `ProposalPreview` fetches without matches and links out. The count on the button is the whole scope, not the card — three cards over a backlog of eleven would read as three items of work. `latest_source_preview()` picks the newest run that still has *unresolved* proposals rather than simply the newest, or a fully-reviewed run would render an empty card while five older proposals waited unseen. A proposal is styled proposed-and-cited and never asserted: green/amber/red are account status and a draft is not one, and the accent is for interaction while "Proposed" is a condition, so the marks take a new dashed `.state-mark.draft` and a muted `.quiet` instead. Both themes captured on the Operate lens.
- **Review debt is one queue item per account, never per run or per proposal.** §8.1's threshold (7 days old or 10 pending) fires once per account with the oldest age and the breached thresholds named, because a queue that grew an item per proposal would bury every other trigger the moment one transcript was extracted. It rides the existing derived-queue path (D-19) at priority 3 — no new store, no new suppression mechanism.

## Account Path Slice 3 — playbooks, plan instances, and governed exceptions (2026-08-05)

- **D-143 — The plan layer schedules requirements and never states one, and migration 0042's tables have no column that could.** Readiness deliberately stores no state; Slice 3 adds the planning layer it declined to store — `readiness_playbook_definitions`, `readiness_playbook_entries`, `readiness_plans`, `readiness_plan_instances`, `readiness_exceptions`, and `readiness_checklist_requirement_map` — and every one of them holds *when something was expected* or *who excused it*, never *whether it is true*. A schema-introspection test walks all six and fails on any column named or suffixed `state`, `met`, `freshness`, `coverage`, `applicability`, `score`, or `weight`, because a cached evaluation is exactly the column somebody adds for convenience and it would be the second source of truth `RELATIONSHIP-READINESS-SPEC.md` §2 forbids. A due date therefore rides *beside* the four readiness axes and is allowed to say `overdue`, which is a claim about the plan, not about the evidence. 30 tests in `tests/test_account_path_slice3.py`; full suite 474 green.
- **Playbook versions do not retire each other, unlike readiness definitions.** Readiness allows one live version per definition key; a playbook cannot, because an account stays pinned to the version it instantiated and that version must remain readable while the plan is live. Editing a template is therefore not a plan edit: `enterprise-launch` v2 ships in the same migration as v1 precisely so an upgrade preview has a real diff to show, and a v1 plan keeps its v1 dates until an operator applies the upgrade. `preview_upgrade` returns additions, removals, timing changes, definition changes, necessity changes, and `recorded_complete_at_risk`, and writes nothing.
- **`not_applicable` and a waiver are different claims, and neither can buy a `met`.** NA removes the question — the component reports `not_applicable` and leaves its pillar's aggregation. A waiver keeps the state exactly where the evidence put it and only clears `missing`. Both are *reported*, never dropped: a suppressed component still renders, a fully-suppressed pillar returns `not_applicable` rather than `met`, a partially-suppressed one names the count in its reason, and `suppressed_count`/`waived_count` ship on the wire. Dropping a suppressed component would let a pillar reach `met` because its only failing condition was excused, which is a suppression buying a pass.
- **A required playbook entry cannot be excluded at instantiation, and the 422 names the governed alternative.** Excluding it would let a plan disagree with the playbook it claims to be. The error says to mark the requirement not applicable instead — refusing without naming the alternative just invites a worse workaround.
- **A legacy checkbox is carried as a planning fact and never becomes evidence.** The compatibility migration maps on exact `template_key` only (§13.5.2 forbids label matching), so `Lock a baseline` and `Baselines captured` do not merge; `done` sets `recorded_complete`, and the resulting `evidence_missing` report genuinely evaluates readiness per scope and lists only the ticks whose state is not `met`. An `na` item *proposes* an exception and never applies one — a migration is not an actor with a reason. Two template keys deliberately map to `budget_authority_evidence` in the seed so the `ambiguous` bucket is exercised rather than theoretical; the second is reported and stays a legacy row. Nothing is deleted, and unmatched items stay readable with `state`/`freshness`/`applicability` all `null`, because a synthesised state would be a weaker second answer beside the projection.
- **Custom audit verbs ride in the payload, not in the CHECK.** `audit_events.action` is constrained to `create|update|archive|convert|close` in migration 0001. Upgrading a plan wanted `supersede`; widening a constraint every reader depends on for one new verb is the wrong fix, so the event is an `update` carrying `{"event": "superseded_by_upgrade"}` in `after`.
- **The concept was renamed from "activation" to "plan" because the trust-boundary guard was right.** `readiness_plan_instances.activation_id` matched the banned substring in `test_no_individual_usage_field_anywhere`. That test bans `usage/activation/weekly_return/sessions/logins/minutes_used` anywhere in the schema, and weakening it so an unrelated column could keep a name is precisely the erosion it exists to stop. Table, column, index, six Python functions, and two response keys were renamed instead.
- **`_instance_for` fixed a scope bug that silently blanked every due date.** When `evaluate()` is called with a `program_id`, *all* pillars come back in the top-level list with no program of their own, so matching a reading to its instance by `(program_id, key)` and falling back to `(None, key)` was the same lookup twice and matched nothing. The fallback now adds `ctx.program_id` **only** in single-program scope; in all-programs scope an account-scoped reading may never borrow some program's instance, or one program's due date would land on another program's condition.
- **The requirement panel offers no status control, and says so on screen.** `requirementControls()` enumerates every write as data — `navigate`, `create`, or `governed`, writing to a `native_record` or an `exception` — so a test asserts the absence rather than trusting review. Readiness has nothing for a status dropdown to write to; one that appeared to work would be the stored second source of truth. The four axes render in a fixed four-cell grid with a word and a shape each, never a combined badge, so a fresh reading cannot make a stale one look current. Suggested actions keep the dashed treatment that separates a proposal from work on a list, and `Create action` states that the durable requirement link lands in Slice 5 instead of implying one exists.
- **Requirement→native-action dedupe is real logic over an empty link set.** §13.6 dedupes a requirement whose next step is already a linked Task or Commitment, but Slice 5 owns the table that stores the link and matching on labels is what §13.5.2 forbids. `_requirement_action_links()` returns `{}` by construction rather than by accident, so the dedupe path runs today and the Slice 5 change is one query; the response is honest about it via `integration.requirement_actions: "not_connected"`.

## Card and row alignment (2026-08-03)

- **D-132 — Enumerating row containers to opt out of the card sibling margin does not work; cards carry no sibling margin at all now.** D-130 kept `.card + .card` at zero specificity and listed the row containers that should reset it. That failed on the next screen looked at: the Evidence metric grid is an **unclassed** `<div>`, so it could not appear in any enumeration, and its second card inherited a 12px top margin — which both dropped it below its peer and, because the grid stretches, made it 12px shorter (169px vs 157px). The lesson is that an adjacent-sibling margin cannot distinguish a stack from a row, and the set of row containers is open while the set of flow containers needing rhythm is small and knowable. The rule is now `.card-stack > .card + .card` only. Removing the global margin was then verified empirically rather than by inspection: measuring the real visual gap between consecutive cards across Today, Evidence, Commercial, Operations and the lenses surfaced exactly three regressions, two of them genuine (`ValueLibrary`, `Plays`) and one a false positive from cards that space themselves with inline `margin-bottom`. Those two roots carry `card-stack`. Final sweep: no touching pairs, no misaligned row peers, and every stack gap on the spacing scale, identical in both themes.

- **D-130 — `.card + .card` leaked a sibling margin into every row layout, and outranked the stack rhythm it was meant to complement.** Three peer counts on Today visibly failed to line up: the first card sat 10px above the other two. Measured cause — `.card + .card { margin-top: 10px }` is written for vertically stacked cards, but it also fires on grid and flex items, so every card after the first in a row was pushed down while the row's own `gap` already handled spacing. Confirmed in two separate row containers (`.queue-brief` on Today, `.two-col` on Operations), so this was a class of bug rather than one screen. The same rule had a second effect: at specificity (0,2,0) it beat `.stack > * + *` (0,1,0), so stacked cards rendered a 10px rhythm where the system specifies 20px — and 10px is not on the documented spacing scale at all. The rule is now `:where(.card + .card)` at zero specificity with an on-scale `--sp-5`, so any container that owns its spacing wins, plus an explicit `margin-top: 0` for the known row containers. A bare `<div>` stacking cards outside `.stack` still gets a rhythm, which a blunt removal would have broken (two such cases found on Commercial and Operations). Separately, the three peer bands are now equal-width: unequal columns (1.35fr vs 1fr) read as misalignment between peers, the primary band is already distinguished by its surface treatment, and the ≤1000px rule was equalising them anyway.

## Stage 11 measurement contract — observation comparability (2026-08-01)

- **D-103 — A campaign may only difference two numbers that were the same measurement.** §5.1 names four matching criteria plus a programme rule; `_observation_query` enforced two (definition, population), and its docstring claimed otherwise — "Matches on definition, version, unit and population identity" — which is the sentence that stops a reviewer from checking.
