# CLAUDE.md — Valence OS standing rules

These rules apply to every session on this repository. They restate the binding constraints from `Valence-OS-Scoping-Doc.md` and win over any conflicting instruction in an individual prompt except an explicit, deliberate override from Zach.

Read all ten before changing scope. The trust boundaries, design rules, tests-green discipline, decisions log, and **mock-only data** remain binding. Objects and fields outside those specs still require asking first.

Two further documents sit at the root and are **in force for presentation only**: `DESIGN-GUIDE.md` (see the Design section) and `UX-FOUNDATION-SPEC.md`, whose Release 2 is detailed in `ACCOUNT-COMMAND-CENTER-SPEC.md` (Slices 2.0–2.4 implemented; Release 3 directional, not authorized).

- **`INTERNAL-OPS-SPEC.md` is additive and in force for Stage 10** (D-95). It generalizes existing records and adds internal forecasting, asks/escalation, reviews/reporting, coverage, feedback, and portfolio analytics without weakening the single-editor or no-auto-send rules. Its integrity foundations in Stage 10.0 land before later slices.
- **`ADOPTION-CAMPAIGN-SPEC.md` is additive and in force for Stage 11** (Zach, 2026-08-01, D-99). A campaign is a time-boxed, measurable intervention against one stable cohort inside an existing program. It adds one concept and *links* to eleven existing ones — it does not clone tasks, comms, moments, champions, MAP, or the playbook. Its §5 measurement contract is binding and non-obvious: a baseline locks a **series** not a point, comparators must be **disjoint** from the treated cohort, a rolled-back baseline **invalidates** the comparison, and signal-triggered pre/post evaluations carry the regression-to-the-mean caution. The app never writes that a campaign *caused* a change.
- **`ACCOUNT-COPILOT-SPEC.md` is additive and in force for Stage 12** (D-105). A grounded, read-only analyst built as predefined workflows — not an agent. Its non-obvious rules: access control is applied **before** the model, never asked of it; retrieved prose is untrusted data that cannot reach the planner or define a tool; every material claim cites a retrieved record snapshot that actually entails it, and an uncited factual claim fails validation rather than shipping; evidence coverage (`supported`/`partial`/`conflicted`/`insufficient`) replaces model confidence, and a numeric confidence badge is prohibited. **The LLM boundary does not inherit the extraction approval** — copilot payloads are a distinct `CONNECTIONS.md` class with their own runtime switch, and no stage flips it.
- **`ADOPTION-COMMS-SPEC.md` is additive and in force for Stage 13** (D-108). Communication sequences are plans over the existing `comms_entries`, never a sender or scheduler. Sequence state and expected dates are derived; a sent wave is an immutable operator-recorded fact. Session attendance is deployment engagement, calculated only for an explicitly linked cohort invitation wave and explicit audience attendees, with unknown classifications and privacy-floor cases withheld rather than guessed. No individual product usage or open/click tracking is introduced.
- **`RELATIONSHIP-READINESS-SPEC.md` is additive and in force for Stage 15** (D-139). Readiness is a **query-time projection**, never a stored state table — a stored state would be a second source of truth that could disagree with the records it came from. Its non-obvious rules: there is **no composite health score**, six independent pillars only, and the absence is asserted by schema introspection in a test; a definition row *configures* an allowlisted evaluator and can never *create* one, so an unknown evaluator key fails closed into `coverage: partial` rather than dropping a pillar; state, freshness, coverage, and applicability are four **independent** axes, so a fresh component can never make a stale one look current; program evidence never merges across programs, and an account-scoped pillar takes the **strongest** applicability across live programs so a required gap cannot hide behind a scope choice; `unsupported` provenance can explain a thin state but never satisfy a component; and research labels are governance metadata, not UI tiers and not weights. Its RR-2 proposal layer (D-145/D-146) adds the same discipline sideways: there is **one** proposal store — `extraction_runs` and `extraction_proposals`, widened, never a parallel `intake_*` pair and never payloads on `capture_inbox_items` — so a combined review of drafts and capture notes is a **read-model composition**, not a copy, and each side keeps its own status vocabulary and command set. `intent` and `target_type` are separate, the `(intent, target_type)` allowlist lives in Python beside the native write path rather than in a SQL CHECK, no readiness target is allowlisted and no proposal may assert a state, and run/proposal counts are derived on every read rather than stored.
- **`ACCOUNT-PATH-SPEC.md` is additive and in force for the Account Path** (D-141/D-142). It adds the Operate lens's next-best-move, program path, and execution groups as a **query-time, rebuildable projection** — no migration, no stored state, no second "what to do next" that could disagree with the records it came from. Its non-obvious rules: native records remain the only edit and closure targets; ranking is eight deterministic bands computed once on the server and the client never re-ranks; a failing source adapter names itself in `coverage.omitted_sources` and can never suppress canonical work; snooze reuses the queue's `attention_state` overlay rather than growing a second suppression store, and a candidate with no valid three-part key ships `snooze_key: null` and offers `Open source` instead; readiness supplies requirement state in its own vocabulary and is never restated, so execution coverage and readiness coverage stay separate claims; and only a `phase_gate_item` carries a `phase`, so the phase filter narrows to gate items rather than attributing a Task to whatever phase its program happens to be in. Slice 3's planning layer (D-143) adds the same rule one level up: a plan says *when* something was expected and readiness says *whether* it is true, so none of migration 0042's six tables may store a state, freshness, coverage, or applicability value — a schema-introspection test enforces it. A suppression is subtractive and always reported, so a fully-suppressed pillar returns `not_applicable` rather than `met`; a waiver accepts a gap without satisfying it; a legacy checklist tick becomes `recorded_complete` and never a readiness state; and playbook versions do not retire each other, so an upgrade is an explicit previewed action. Slice 5's relationship layer (D-149) applies the rule sideways: none of migration 0046's four link tables may carry a `state`, `status`, `met`, `freshness`, or `coverage` column, because a link table is exactly where a cached "this is satisfied" would be written and would then disagree with readiness. A linked action never becomes evidence, evidence of a kind the definition does not accept attaches with `supporting: false` and moves nothing, `blocked` and `insufficient_data` are different verdicts, and an override records the unmet conditions without satisfying any of them. **A requirement whose action is linked leaves the gap list by design (§13.6) and must stay reachable through the `Tracked by a linked action` disclosure, which is a disclosure and never a second queue** (D-150). Slice 6's shared plan (D-151…D-155) stores nothing and needs no migration: `shared_plan._project` returns a customer `artifact` and an operator `diagnostics` that are **structurally separate documents**, and the artifact is built from promoted records only rather than built whole and filtered late — the filter approach is how a client-facing generator leaks. A readiness reading that has no honest external word is **withheld with a stated reason**, never downgraded to a neighbouring one: a stale `met` is withheld rather than shown `Complete`, a `conflicted` reading is never resolved in the customer's favour, and an unrecognized state falls through to a refusal naming it. Refusal wording is authored on the server as a clause completing "held back because …" and the sentence frame lives in `sharedPlan.withheldSentence`, because **a view that composes any part of a refusal can soften one**. The promotion preview runs the same projection as the export, so it cannot drift from it. Slice 7's measurement layer (D-156…D-161) is **local, aggregate, and about our own surfaces**: migration 0050 records sixteen named events with an account id, a reason code, a ranking rule version, and a rotating session token — no person id, no free text, no record content, and no adapter, because an event never reaches a network boundary — but it is registered in `CONNECTIONS.md` as `product_telemetry_sink` (`gate_status: local`) anyway, because pointing it at a vendor would send behavioural data about how an account is worked out of the installation, which is the data-handling conversation rather than a config change. Turning measurement off **discards what was collected**, and no export or person-identifying field may be added. `views`, `views_with_next_move`, and `views_with_incomplete_coverage` are deliberately separate counters, every event carries its ranking rule version so a funnel cannot average two orderings, and the §17.5 caveat renders beside the numbers because a click-through rate cannot say whether a recommendation was correct — **no numeric quality score belongs here**. A ranking ruleset is selected by the `VALENCE_OS_RANKING_RULES` deployment flag and only *compared* from the UI, which writes nothing; a comparison that reports no reordering is reported honestly rather than manufactured by seeding around it (D-161). And the coverage notice completes the suppression rule in the other direction (D-160): a response the server calls `complete` can still be **subtractive**, so a snoozed row is always stated, quietly and without a status hue, because a withheld row is not a failure.
- **`COMPANY-INTEL-SPEC.md` is additive and in force for Stage 14** (Zach, 2026-08-02, D-110). Public company artifacts are immutable, span-cited, proposal-first mock records linked through a canonical company entity separate from the account. Only confirmed events with live evidence can annotate whitespace, enter a brief, or compose persisted convergence. Independence requires different kinds, occurrences, and origin groups; republications do not corroborate themselves. Source correction/retraction invalidates unsupported derivatives. Retrieval and extraction remain separate fail-closed connection classes.

- **`ACCOUNT-INTAKE-SPEC.md` is additive and in force for the account drop zone** (Zach, 2026-08-06, D-206…D-209). All four slices are built (D-210…D-238, D-242…D-247). Drop or paste on the Operate lens → screen → detect kind → parse **from bytes** → the existing extractor → `_persist_run` → the existing `ProposalReview`. Its non-obvious rules: **the receipt resolves nothing** — there is one review surface, and two surfaces that both resolve proposals would eventually disagree about what a command means; kind detection is regex and structure and is **never the model's decision**, because a document that could pick its own parser could decide which of its own text counts as new; **text in, bytes never *persisted***, so decoding happens inside the per-kind parse rather than before it, and an `.eml` decodes per MIME part with the charset that part declares; a document naming another account is **reported and does not move**, since automatic re-scoping is the injection payload writing itself; every refusal and coverage sentence is authored on the server because a view that composes part of an "I did not do this" statement can soften one; and `intake_drops` stores only what `extraction_runs` does not, with `outcome` the single named exemption in the forbidden-column test. Slice 2's rule is the one with the longest reach: **a dropped `.eml` produces the same records a synced one does** (§7.4) — one ingestion path differing only by a `DropOrigin`, with both dedupe checks outside the branch — because relationship-health signals are counts over our own correspondence, and divergence there surfaces as quietly wrong numbers rather than an error. Slice 3 (D-226…D-238) needed no migration and applies the same discipline to every proposal, not only dropped ones: **a citation must be the quote, or say it is not** — the located passage is byte-identical to the span or the pane reports it unlocatable and marks nothing, there are exactly two match strategies and no similarity threshold, and a run has a retained document *iff a drop points at it* (never `interactions.raw_notes`, whose mutability would make it a fabricated provenance claim). Deleted, never-captured, and unlocatable each **degrade** the citation and none removes the span. Duplicate detection sits **after the refusal and before any parse**, so a refused kind keeps its own sentence, and a duplicate receipt names the earlier drop because silent dedupe is indistinguishable from a failed upload. Accept-all is a **dry run of the accept path** over a run's *open* proposals, all-or-nothing and never account-wide; `run_id` is a filter on the one queue whose withheld remainder is always stated. Slice 4 (D-242…D-247) added `("create", "milestone")` and §17's six drop events, and needed **no migration**: the new target is a normalized `(intent, target_type)` pair whose legacy `mutation_type` is NULL — which is what 0043 made that column nullable for — so every dispatch reads `target_type` rather than stripping a prefix off a name that does not exist. A milestone proposal may name a milestone and a date and **nothing else**; a date is never guessed from a relative phrase and never parsed from a slash form, a program is never inferred from the text, and each refusal is a server-authored sentence landing in its own coverage key. The six events carry no filename, kind, size, or count, because **a filename is document content by another name**.

- **Do not re-gate work that is no longer gated** (Zach, 2026-07-31, D-83). The frozen-scope regime and the Phase 2 evidence gates are retired; deferring a feature for "scope discipline," marking a design decision as blocking, or downgrading a schema change to a request for permission all reintroduce a gate that was deliberately removed. Defer something only when a *fact* forces it — data that does not exist yet, elapsed time that has not passed — and say which fact. The one standing gate is the data-governance one below.

## Trust boundaries (schema-level, non-negotiable)

- No table, column, or field may exist anywhere for a named individual's usage of the Nadia product. Champion engagement means deployment engagement (meetings, comms, advocacy), never product usage. Cohort usage data is aggregate only.
- Visibility works by inherited safe defaults: raw notes, stakeholder judgments, commercial strategy, and AI-generated interpretations default to internal-only. Generated client-facing outputs include only affirmatively promoted records, enforced in the generator code, not by convention.
- Stakeholder assessments (stance, influence, relationship strength) always carry a date and an evidence note.
- No sensitive personal data on people, ever: nothing on health, family, politics, or anything a works council would object to. People notes are professional observations only; rapport notes stay professional. Relationship-health signals (reciprocity, attendance, response time) are counts and distributions derived from our own correspondence — never sentiment inference, never product usage.

## Data rules

- Mock/synthetic data only. No real client names, people, transcripts, or figures anywhere in this repo, including tests, seeds, comments, and commit messages.
- Canonical external data (CRM, Data team metrics) is read-only locally; operational interpretations go in labeled overlay fields with rationale, author, and date. Never recompute metrics; ingest them.
- No hard-coded benchmarks (no "75% weekly return" or similar in code or UI copy). Benchmarks are data: versioned, sourced, with population and period.
- Last-touch dates are derived from interactions, never hand-edited.
- Stale metric-derived indicators render as unknown, never as carried-forward good state.

## Engineering defaults

- SQLite with versioned migrations from the first table. Every schema change is a migration; no manual DB surgery.
- Soft-delete and archival for operational objects; append-only audit log for material changes (actor, timestamp, before/after, source).
- Long-running work goes through the job table; routine edits and navigation must feel instant.
- Timestamps in UTC; contractual dates (renewal, notice) stored as dates, not timestamps.
- Keep it boring: no caching layers, no external queues, no microservices, no speculative abstractions. The dataset is a few thousand rows.

## Design

- `DESIGN-GUIDE.md` is the standing design authority. It supersedes §6 of the
  scoping doc and the navigation inherited from the §5 module list. Read it
  before any frontend change.
- `UX-FOUNDATION-SPEC.md` is the additive authority for canonical navigation,
  saved portfolio views, and the staged command-center/activity/outcomes path.
  Release 1 preserves the current account-tab taxonomy and trust boundaries.
- No raw hex values, no arbitrary pixel values. Everything comes from
  `tokens.css`. Both light and dark are first-class; a change that only works
  in one theme is not done.
- Color carries meaning only. Green, amber, and red are reserved for status.
  The accent is for interaction, never for state. The budget waterfall is the
  single documented exception and never shares a screen with status indicators.
- No state is conveyed by color alone. Every status pairs a color with a shape
  or a label.
- Every dated record shows the freshness language: age chip, decay ramp, and
  the cross-hatched unknown treatment for anything past its threshold. Stale
  data never renders as carried-forward good state.
- Navigation is Today, Accounts, Library, Operations. Account-scoped work lives
  in the account workspace tabs. Do not add a new top-level destination without
  asking.
- Capture is global and keyboard-first, never a place you navigate to.
- Quality floor is non-negotiable: 4.5:1 contrast audited in both themes,
  visible keyboard focus, semantic tables, `prefers-reduced-motion` and
  `color-scheme` honored, no flash of incorrect theme.
- After any structural UI change, re-verify the §2 trust boundaries still hold:
  no individual product usage anywhere, client-facing outputs include only
  promoted records, stakeholder assessments keep date and evidence.
- Schema changes are proposals, not blockers. Batch them with a one-line
  rationale and present them at the end of the phase.

## Process

- Log non-obvious implementation decisions in `decisions.md` with a one-line rationale.
- When the scoping doc is silent, build the smallest thing that passes the acceptance test. When it contradicts itself, stop and ask.
- The 30-second capture rule wins every tie: if a design choice makes post-call capture slower, choose the other design.
